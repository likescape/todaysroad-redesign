# 스팟 첫 구현: 작업 방식과 실행 프롬프트

## 작업 방식 판단

현재 `todaysroad-redesign`의 프런트엔드 목업에 스팟 경험을 추가하는 첫 구현은 단일 에이전트로 진행한다. 자료 해석 → 스팟 모델 정의 → 코스 연결 → 화면 구현이 긴밀히 이어지고, 주요 화면의 상태가 `components/AppScreen.tsx`에 모여 있어 구현을 여러 에이전트로 나누는 이점이 작다.

이 판단은 실제 데이터 수집 파이프라인, 운영 서버, 도보 경로 탐색까지 만드는 작업을 포함하지 않는다. 향후 여러 지역의 자료 조사와 위치 검증, 서버 개발, 앱 개발을 독립적으로 진행할 때는 작업별 입출력과 파일 소유권을 정한 뒤 서브 에이전트 사용을 검토한다.

확인한 근거:

- 현재 앱에는 `Course`와 산책 기록 모델이 있지만 스팟 모델은 없다.
- `../todays-road-mono/data-discovery/`에는 이야기 카드와 건축물대장 예제가 이미 있다.
- `mixed-card-candidates.json`의 6개 후보는 모두 `eligible_for_automatic_display: false`이고 코스 연결은 미검증이다. 이 중 좌표가 있는 문화행사도 코스 연결과 날짜 조건을 따로 판단해야 한다.
- `building-selected.json`에는 실제 대장 정보와 주소가 있지만 코스와의 위치 관계는 미검증이다.
- 현재 추천 경로는 도로망을 따라 탐색한 경로가 아니라 수학적으로 생성한 목업 경로다.

실행 순서: 현재 상태 확인 → 콘텐츠와 위치 근거 점검 → 모델·노출 규칙 정의 → 코스 생성·미리보기·산책 중 화면 연결 → 기능·화면 검증.

아래 프롬프트는 구현 실행용이다. 이 문서를 작성하는 단계에서는 앱 코드를 변경하지 않았다.

## 복사해서 사용할 실행 프롬프트

```text
현재 작업 폴더의 ‘오늘의길’ 프런트엔드 목업에 스팟 기능의 첫 버전을 구현하라.
단일 에이전트로 수행하고, 설계 설명에서 끝내지 말고 구현과 검증까지 완료하라.

[목표와 스팟의 정의]
스팟은 ‘산책 중 어떤 장소를 새롭게 바라보게 만드는 작은 발견’이다.
장소와 그 장소에 얽힌 이야기가 함께 있어야 한다.
코스는 산책의 흐름을 만들고 스팟은 그 안에서 기억에 남는 순간을 만든다.
사용자가 산책을 마친 뒤 ‘30분 걸었다’와 함께 ‘오늘 동네에 대해 하나 알았다’를 얻도록 한다.

예시는 철길에서 공원으로 바뀐 장소, 건물의 기록을 알고 올려다보게 되는 순간,
동네 이름의 유래나 과거와 현재의 변화다. 유명 관광지 여부는 선정 기준이 아니다.
장소성·발견성·산책과의 어울림을 기준으로 콘텐츠를 고른다.
좌표나 시설명만 있는 POI, 원자료의 숫자 나열만으로는 좋은 스팟이 완성되지 않는다.
스팟은 선택적으로 읽는 발견 콘텐츠이며 필수 경유지·체크포인트가 아니다.

[작업 대상과 읽을 자료]
구현 대상: 현재 폴더 todaysroad-redesign.
자료 참고: ../todays-road-mono/data-discovery/.
참고 저장소는 읽기 전용으로 사용하고 필요한 정제 데이터만 현재 프로젝트에 추가한다.

먼저 적용되는 AGENTS.md와 git status를 확인하고 기존 작업을 보존하라.
현재 프로젝트에서 다음을 읽어 실제 구현과 연결 지점을 파악하라.
- README.md, docs/community-requirements.md
- lib/courses.ts, lib/recommend.ts, lib/walk.ts
- components/AppScreen.tsx, KakaoMap.tsx, CourseSheet.tsx, WalkOverlay.tsx
- lib/journal.ts, lib/useJournal.ts, components/JournalUI.tsx
- components/ThemeProvider.tsx, app/globals.css, package.json, tests/

data-discovery에서 다음을 읽고 필요한 원본·검증 파일까지 대조하라.
- README.md, MIXED-CARDS.md, BUILDING-EXAMPLE.md
- mixed-card-candidates.json, building-selected.json, card-candidates.json
- 관련 manifest와 validation 파일

같은 상위 폴더에 있는 모노레포의 운영 앱과 현재 목업을 혼동하지 마라.

[첫 구현 범위]
기존 코스를 생성·선택하면 해당 경로 주변의 적격 스팟을 함께 제안하고,
시작 전과 산책 중에 같은 스팟의 이야기를 열어 볼 수 있게 하라.
처음에는 기존 신수동·광흥창 인근 자료를 중심으로 소수의 콘텐츠를 정제한다.
서버, 인증, 자동 수집 파이프라인, 새로운 도보 경로 엔진, 개인화 모델은 이번 범위에 넣지 않는다.
스팟 때문에 코스를 다시 생성하거나 반드시 방문하도록 요구하지 않는다.
방문 인증, 배지, 알림, 커뮤니티 공유 확장은 이번 범위에 넣지 않는다.

[콘텐츠 선정과 근거]
후보마다 아래 세 질문에 답하고 채택·보류 사유를 짧게 기록하라.
1. 장소성: 왜 이 장소에서 들려주는 이야기인가?
2. 발견성: 읽은 뒤 무엇을 새롭게 보거나 이해하게 되는가?
3. 산책과의 어울림: 짧고 가볍게 읽으며 걷는 즐거움을 더하는가?

카드는 짧은 발견 제목, 장소 이름, 핵심 이야기 1~3문장으로 작성하라.
주변을 다시 보도록 돕는 짧은 관찰 제안을 넣을 수 있지만 현장에 없는 특징을 만들어내지 마라.
상세에는 필요한 추가 설명, 출처 링크·기관·확인일·자료 기준 시점을 제공하라.
흥미를 위해 사실을 과장하거나 출처에 없는 역사·건축적 의미를 덧붙이지 마라.

원자료의 구분을 유지하라.
- 사용승인일을 최초 준공일이나 착공일로 바꾸지 않는다.
- 대장에 기재된 높이를 현장 실측값으로 표현하지 않는다.
- 공원 전체의 연혁·길이를 특정 구간만의 정보로 표현하지 않는다.
- 전승은 전해지는 이야기로 표현하고 역사적 사실과 구분한다.
- 과거 상권 통계는 그 기간과 지역 전체의 통계다. 특정 가게의 현재 상태로 바꾸지 않는다.
- 행사 정보는 날짜와 확인 시점을 기준으로 판단한다. 저장된 days_until_start를 현재 값으로 재사용하지 않는다.
- 데이터가 있다는 이유만으로 모든 자료 유형을 첫 화면에 넣지 않는다.

[장소와 코스의 연결]
이야기의 근거 확인과 위치·코스 연결 검증을 별개로 취급하라.
data-discovery의 기존 후보는 그대로 자동 노출할 수 있는 완성 데이터가 아니다.
검증 상태가 바뀌면 새 근거를 남기고 원본의 상태를 조용히 덮어쓰지 마라.

주소·장소 식별을 대조하고, 이용 가능한 공식 자료나 지오코딩 도구로
실제 장소의 좌표를 보완할 수 있는지 확인하라. 위치 근거와 정확도 한계를 보존하라.
긴 공원은 실제 대상 구간을 확인하고 다른 구간의 대표 핀을 가져다 쓰지 마라.
상권 통계는 유효한 영역이 확인되기 전 특정 건물의 점 좌표에 붙이지 마라.

위치가 확인된 점형 후보에 대해 경로의 모든 선분과의 최소 거리를 계산하라.
출발점까지의 거리나 경로 꼭짓점까지의 거리만으로 매칭하지 마라.
초기 목업의 후보 반경은 100m로 두되 조정 가능한 설정값으로 관리한다.
이 값은 제품 검토용 가정이며 실제 도보 접근성·진입 가능성을 보장하지 않는다.
표현은 ‘경로 주변’으로 하고 ‘반드시 지나는 곳’이나 ‘도보 몇 분’으로 단정하지 않는다.

적격 후보 중 코스당 최대 3개를 선택하고 경로 진행 방향 순으로 정렬하라.
가까운 같은 장소·같은 이야기의 중복을 줄이고 적격 후보 안에서 소재의 다양성을 고려하라.
반경 밖 후보나 근거가 부족한 후보로 개수를 억지로 채우지 마라.
같은 입력에는 같은 결과가 나오도록 동률 처리 기준을 정하라.
생성 또는 선택된 코스의 스팟 목록은 시작 전과 산책 중에 동일하게 유지한다.

자료가 부족하면:
- 확인되지 않은 장소 좌표를 임의로 만들거나 실제 위치처럼 지도에 표시하지 않는다.
- 실제 코스에는 적격 스팟이 0개인 상태를 정상 지원한다.
- 확인된 이야기의 카드 UI는 위치 미검증임을 표시한 개발 전용 미리보기에서 검토할 수 있게 한다.
- 지도 상호작용용 합성 fixture가 필요하면 실제 장소와 분리하고 예시 데이터임을 명확히 표시한다.
- 보완하지 못한 위치 정보와 검증 범위를 결과 문서에 구체적으로 남긴다.

[데이터 구조와 구현]
기존 구조에 맞는 최소 모델을 정의하라. 다음 개념을 구분해 담아라.
- 장소: 안정적인 id, 이름, 주소, 확인된 좌표 또는 null, 위치 근거·검증 상태
- 이야기: 제목, 핵심 문장, 상세, 소재 유형, 사실·전승·통계·행사의 구분
- 근거: 출처 URL·기관, 원자료 파일·식별자, 확인일, 자료 기준일·유효 기간, 한계
- 코스 연결: spotId, 경로까지의 거리, 경로상 진행 위치와 표시 순서

한 장소에 여러 이야기가 있을 수 있도록 장소 정체성과 콘텐츠를 구분하되 과도하게 일반화하지 마라.
콘텐츠와 특정 코스와의 연결 정보를 분리하라.
선별 함수는 UI와 분리하고 시간 의존 조건은 기준 날짜를 주입할 수 있게 하라.
기존 Course에 선택적인 스팟 연결을 추가해 스팟 없는 예전 코스도 정상 동작하게 하라.
원본 ZIP·HTML 전체를 클라이언트 번들에 포함하지 마라.

[사용자 경험]
1. 코스 생성·선택 완료:
   기존 코스 카드에 ‘이 길에서 발견할 이야기’ 영역을 추가한다.
   간결한 제목과 장소를 보여 주고 탭하면 상세를 연다.
   스팟이 없어도 코스 확인·산책 시작은 그대로 가능하다.
2. 지도:
   현재 코스의 스팟만 기존 코스 마커와 구분해 표시한다.
   마커와 목록 항목은 동일한 상세를 열고 선택 상태가 서로 일치한다.
3. 상세:
   장소와 이야기를 먼저 보여 주고 출처·기준일은 상세에서 확인하도록 한다.
   닫으면 원래 코스 화면 또는 진행 화면으로 돌아간다.
4. 산책 중:
   스팟 목록을 다시 열 수 있는 작은 진입점을 둔다.
   자동 팝업이나 강제 정지 없이 사용자가 선택해서 읽게 한다.
   상세를 열거나 닫아도 타이머·경로·진행 위치가 유지되어야 한다.
   현재 이동은 시뮬레이션이므로 실제 도착·방문 완료로 표시하지 않는다.

기존 잎 테마, 라이트·다크 모드, 390×844 데스크톱 화면과 모바일 대응을 따른다.
산책 시작·종료, 현재 위치, 하단 탭이 새 UI에 가려지지 않게 하라.
키보드 조작, 상세 닫기, 포커스 복귀를 기존 공용 컴포넌트에 맞게 처리하라.
새 코스 선택·재생성·홈 복귀 시 이전 스팟 선택 상태가 남지 않게 하되
산책 중 탭·설정·테마를 오갈 때 진행 중 코스와 스팟은 유지하라.
첫 버전에서는 산책 기록·커뮤니티의 저장 구조와 스팟 방문 이력을 확장하지 않는다.

[검증과 완료 기준]
행동을 검증하는 필요한 테스트를 추가하라.
- 위치 미검증·범위 밖 후보 제외, 선분 중간에 가까운 후보 포함
- 중복 제거, 최대 개수, 순서, 동일 입력 결과의 안정성
- 스팟 0개와 좌표 없는 후보 처리
- 날짜 조건을 구현했다면 기준일 전후의 행사 노출
- 코스 선택부터 산책 시작까지 같은 스팟 목록 유지

npm test와 npm run build를 실행하고 새 오류를 해결하라.
기존 오류가 있다면 이번 변경으로 생긴 오류와 구분하라.
README의 카카오맵 실행 조건을 확인하고 로컬 3000 포트에서 브라우저로 검토하라.
이미 실행 중인 서버가 있다면 확인 후 활용하고 다른 프로세스를 임의 종료하지 마라.
라이트·다크, 모바일·데스크톱, 코스 생성 → 스팟 상세 → 산책 시작 →
산책 중 상세 → 닫기 → 종료와 기존 기록·커뮤니티 흐름을 확인하라.
지도 SDK를 사용할 수 없다면 대체 검증과 실제 지도에서 확인하지 못한 범위를 구분해 보고하라.

완료 조건은 ‘코스를 고른 사용자가 그 길 주변의 장소 이야기를 선택해 읽고,
기존 산책 흐름으로 자연스럽게 돌아올 수 있음’이다.
```
