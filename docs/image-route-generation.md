# 이미지 기반 산책 코스 생성

`코스 생성 → 추천 받기`는 이제 무작위 타원이 아닌 지도 이미지 분석 결과를 사용한다. 지역별 도로·POI 데이터베이스나 길찾기 API는 호출하지 않는다. 카카오 지도는 래스터 이미지 공급과 이미지 좌표의 위경도 변환에만 사용한다. 기존 스팟 이야기는 경로 완성 뒤 선택적으로 붙으며 경유지 선정에는 쓰지 않는다.

## 실행 설정

기본 개발 모드는 설치된 Codex CLI의 기존 로그인을 사용한다. `codex login status`가 성공하면 별도 OpenAI API 키 없이 실행한다. 로그인 토큰을 읽거나 API 키로 전용하지 않는다.

```dotenv
NEXT_PUBLIC_KAKAO_MAP_KEY=<기존 카카오 JavaScript 키>
MAP_VISION_PROVIDER=codex
# CODEX_BIN=/usr/local/bin/codex
# CODEX_MAP_VISION_MODEL=<선택 사항: 생략하면 설치된 CLI 기본 모델>
```

Codex는 별도 임시 폴더에서 `--ignore-user-config --ephemeral --sandbox read-only`로 실행한다. 셸 도구와 웹 검색을 끄고 이미지와 JSON 스키마를 전달한다. 분석은 OpenAI 서버에서 수행한다. 취소·시간 초과 시 프로세스를 종료하고 임시 이미지와 결과를 삭제한다. 기존 API 방식은 `MAP_VISION_PROVIDER=openai`와 서버 전용 `OPENAI_API_KEY`를 명시하면 사용할 수 있다. 선택적 API 모델 변수는 `OPENAI_MAP_VISION_MODEL`이며 기본값은 `gpt-4.1`이다.

이미지 분석은 중심 주변의 길 15~40개와 인접 요소 5~15개를 우선 추출한다. 요청 범위의 상한은 노드 60개·길 60개·요소 25개이며 지도 전체의 건물을 열거하지 않는다. `local_road`는 지도에 그려진 좁은 생활도로·골목 유형을 뜻한다. 별도 보도 기호가 없다는 이유만으로 이 유형을 모두 불명확하게 처리하지 않으며, 실제 보행 가능 여부는 별도로 확인해야 한다.

```bash
npm run dev
npm test
npm run build
```

서버는 `127.0.0.1:8000`에 바인딩한다. 카카오 Web 도메인에 등록한 `http://localhost:8000`에서 실행한다. Codex 분석 엔드포인트는 로컬 호스트 요청만 받으며 프로덕션에서 자동 활성화되지 않는다.

## 참고 문서 사용 범위

`output/visualizations/image-route-flow-preview.html`에서는 **1~7단계 순서만** 참고한다. 가상 도형·예시 경유지·경로·검증 상태·결론은 이번 실행의 데이터나 근거로 사용하지 않는다.

## 7단계와 코드

| 단계 | 구현 | 주요 코드 |
| --- | --- | --- |
| 1. 현재 위치 주변 지도 스냅샷 | GPS 위치를 확인하고 별도의 1024×1024 일반 지도를 만든다. 타일 완전 로딩·픽셀 커버리지를 검사하고 같은 출처의 제한된 타일 중계를 거쳐 Canvas에 합성한다. 희망 시간에 따라 3/4/5 레벨을 사용한다. 앱 UI·마커·기존 경로·다크 색 보정은 캡처에 포함하지 않는다. | `lib/map-snapshot.ts`, `components/KakaoMap.tsx`, `app/api/map-tile/route.ts` |
| 2. 길·자연·건물·아이콘 구분 | 서버가 이미지 자체를 비전 모델에 보내 길 중심선, 명시적 교차점, 자연/건물 폴리곤, 아이콘 및 접근 가능한 길의 노드를 구조화해 받는다. 좌표·ID·연결 참조·배열 크기를 다시 검사한다. | `lib/map-vision.ts`, `lib/map-segmentation.ts`, `app/api/map-segmentation/route.ts` |
| 3. 산책 전략 | 4km/h 기준으로 목표 거리를 잡는다. 인식 신뢰도 0.8 미만, 자동차전용도로, 불확실한 길을 제외한다. 물·건물 폴리곤과 교차하는 선분은 제외하고 평지 선호 시 계단도 제외한다. | `lib/image-route-planner.ts` |
| 4. 카테고리 필터링 | 자연→공원/숲/산/물, 강변→물, 카페→카페 아이콘·라벨 등 이미지에서 읽힌 장소 유형을 사용한다. 선호 분위기는 관측된 장소 유형의 대리 기준이다. | `CATEGORY_TAGS` |
| 5. 웨이포인트 선정 | 이미지가 가리킨 접근 노드가 출발점과 연결되고, 장소 표식/경계에서 100m 이내이며, 시간 상한 내에 왕복할 수 있는 후보만 남긴다. 카테고리 다양성을 보존한 최대 10개 후보 중 최대 3개를 선택한다. | `planImageRoute` |
| 6. 길 연결 | 명시적 노드 연결만으로 그래프를 만들고 Dijkstra로 구간을 연결한다. 이미지에서 선이 교차한다는 이유로 교차점을 만들지 않는다. 카테고리 충족 수, 목표 거리 차이, 중복 구간을 비교해 경유 순서를 정한다. | `planImageRoute` |
| 7. 완성 | 캡처 당시 WCONG 좌표 변환을 보존하여 경로를 위경도로 되돌린다. 완성된 길의 실제 길이로 거리·예상 시간을 표시하고 같은 경로로 산책을 시작한다. | `lib/recommend.ts`, `components/AppScreen.tsx` |

## 실패와 결과 표시

- 현재 위치 확인 실패·큰 위치 오차·지도 타일 누락·분석 실패·잘못된 응답·경유지 부재·경로 단절 시 코스를 만들지 않는다. 무작위 또는 직선 대체 경로는 없다.
- 출발 위치는 가장 가까운 인식된 길로 투영한다. 60m보다 멀면 실패한다. 5m 넘게 떨어졌으면 결과에 거리를 알린다. 현 위치→길까지의 불확실한 구간은 코스에 그리지 않는다.
- 건물·물의 중심을 통과하지 않고 **장소 주변의 연결된 길**을 경유한다. 실제 출입구를 검증했다는 뜻은 아니다.
- 희망 시간의 130%를 초과하는 경로는 제외한다. 적절한 길이가 없으면 실제로 연결한 짧은 코스와 시간 차이를 알린다. 100m 미만 경로는 제안하지 않는다.
- 미반영 카테고리, 동일 구간 왕복, 계단 포함, 경사 미확인 등을 표시한다. 조용함·활기·야경·평지는 실제 소음·혼잡·조명·경사의 측정 결과가 아니다.
- 지도와 카드에 경유지 번호를 표시한다. `지도에서 찾은 요소 보기`에서 스냅샷·인식한 요소·완성 경로를 겹쳐 검토한다. 주황 선은 인식된 길 후보이며, 초록 선은 최종 경로다.
- 단계 표시는 실제 처리 진입 시 갱신한다. 짧은 로컬 계산 단계 3~6은 React 렌더링에서 한 번에 지나갈 수 있다. 가짜 대기시간은 넣지 않는다.
- 생성 취소·홈 복귀·다른 코스 선택·언마운트는 진행 중 요청을 중단하고, 늦게 온 결과가 이전 코스를 다시 띄우지 못하게 한다. 재시도·조건 변경 시 이전 선택을 유지한다.
- 고정 예시 코스에 경로가 없으면 `주변 코스 만들기`로 새 생성 흐름에 진입한다. 예시 클릭 때도 임의 타원을 만들지 않는다. 기존 `preview=walk/course/spots`의 명시적 디자인 검토 경로는 유지한다.

## 현재 구현 범위와 한계

이는 **범용 비전 모델이 지도에서 벡터 영역과 길 중심선을 추출하는 프로토타입**이다. 학습된 전용 픽셀 단위 세그멘테이션 모델, 라벨별 IoU 평가, 전국 실측 도보 검증을 완료한 제품이 아니다. JSON 구조 검증과 장애물 교차 검증은 모델이 놓친 건물·횡단보도·통행 제한까지 검출하지 못한다. 범용 비전 모델의 정밀 위치 추론에는 오류가 있을 수 있으므로 전국 도보 내비게이션 정확도를 주장하지 않는다.

한 장의 지도에서 보이는 영역만 다루며, 가려진 길을 복원하지 않는다. 넓은 지도에서는 작은 아이콘과 골목이 빠질 수 있다. 산 내부는 초록 영역이라고 걸을 수 있는 곳으로 취급하지 않는다. 다리·고가·터널·출입 제한·공사 상황·실제 보행 가능 여부는 확인되지 않을 수 있다. 확실하지 않은 다리 접근이나 물과 겹치는 경로는 보수적으로 제외한다.

다음 품질 단계에서는 전용 세그멘테이션 모델이 같은 `MapSegmentation` 계약을 출력하도록 `analyzeMapImage`를 교체하고, 실제 지도 이미지와 사람이 검수한 마스크/길 연결을 비교해야 한다. 다중 스냅샷 병합·확대 재분석은 이번 범위에 포함하지 않는다.

산책 진행의 거리·이동 표시는 기존과 동일한 시뮬레이션이다. 새로 실제 GPS를 사용하는 부분은 코스 생성의 **출발 위치 확인**이다.

## 데이터와 서버 처리

- 사용자에게 지도 이미지의 OpenAI 전송을 추천 패널에서 안내한다. 지도 이미지가 위치를 드러낼 수 있다. 정확한 GPS 좌표는 모델 입력에 별도로 넣지 않는다.
- Codex는 CLI의 저장된 로그인을 사용한다. 선택적 API 모드의 키는 서버에만 있고 Responses 요청은 `store: false`다. CLI의 `--ephemeral`과 API의 `store: false`는 서로 다른 설정이며 공급자의 전체 보관 정책을 대신하지 않는다.
- 지도 스냅샷·세그멘테이션·경유지는 선택/진행 중 코스의 메모리에만 둔다. 기존 산책 기록·커뮤니티 게시글에 지도 이미지를 저장하지 않는다.
- 지도 타일 중계는 카카오 SDK에서 확인한 `mts[0-3]?.daumcdn.net/api/v1/tile/PNG02/.../latest/...png`만 허용한다. HTTPS로 바꾸고 리다이렉트·쿼리·자격 증명·다른 포트/호스트를 거부한다. SDK 타일 URL 형식이 바뀌면 이 어댑터를 갱신해야 한다.
- 분석 입력 6MB, 응답 2MB, 타일 512KB로 스트림을 제한한다. Codex 요청은 300초(API 모드는 110초), 전체 생성은 345초로 제한한다. 분석 동시 요청은 서버 프로세스당 2개다.
- 이 저장소의 기존 데모에는 사용자 인증이 없다. 동시 요청 제한은 사용자별 비용 제한/인증을 대신하지 않는다. 외부 운영 시 인증·사용량 제한과 지도 이미지의 재사용·외부 분석에 필요한 공급자 조건을 운영 환경에서 확정해야 한다.

## 검증

`npm test`는 기존 산책 기록/스팟/테마 검사와 함께 다음을 검사한다.

- 서로 다른 위도/경도에서 같은 이미지 그래프의 경로·거리 계산
- 카테고리 경유지 통과와 출발 길로의 복귀
- 건물/물의 얇은 경계 통과 차단, 단절된 노드·불확실한 길·자동차전용도로 제외
- 영상 위에서 교차해도 연결되지 않은 길의 분리
- 현재 위치의 길 투영, 무단 직선 연결 없음, 너무 먼 출발점 실패
- 실제 경로 길이·왕복·희망 시간 차이·미반영 조건
- 응답 구조, 안전한 타일 URL, 스트림 크기 제한
- 실제 스냅샷 입력 전달, 7단계 진행, 설정 누락 시 GPS 호출 안 함, 취소 처리

`http://localhost:8000/dev/image-route`는 개발 모드에서만 제공한다. 현재 위치 또는 서울 신수동·부산 시민공원·제주 탑동의 공개 좌표로 지도를 캡처하고 2~7단계를 진행한다. 단계 버튼으로 원본 지도, 인식 요소, 제외된 길과 사유, 장소 후보, 경유지, 최종 코스를 확인한다. 원본 PNG와 분석 JSON을 저장할 수 있고 실패 단계에서도 중간 결과를 유지한다. 카테고리를 바꾸면 기존 분석으로 경로만 다시 계산하며 위치·시간 변경 시 새 지도를 캡처한다. 이 페이지의 테스트 위치는 앱의 GPS 실패 시 대체 위치로 사용되지 않는다.

자동화 검사는 합성 그래프의 기하/연결과 가짜 CLI 프로세스의 이미지 전달·응답 검증·취소·임시 파일 정리를 검사한다. 이를 실제 지도 인식 정확도나 전국 생성 성공률의 근거로 사용하지 않는다.

공개 테스트 좌표가 길에서 60m 넘게 떨어져 있으면 가장 가까운 인식된 길과의 거리를 표시하고, 사용자가 그 길을 테스트 출발점으로 선택할 수 있다. 같은 이미지의 분석을 재사용해 3~7단계를 다시 계산한다. **내 현재 위치 모드와 실제 앱에서는 이 테스트용 선택을 제공하지 않으며**, GPS 출발점 제한을 그대로 적용한다. 원래 좌표에서 새 출발점까지 임의의 연결선을 그리지 않는다.

## 공식 API 근거

- [Codex 비대화형 실행](https://learn.chatgpt.com/docs/non-interactive-mode): 저장된 인증 재사용과 구조화된 최종 결과.
- [Codex 인증](https://learn.chatgpt.com/docs/auth): ChatGPT 로그인과 API 키 로그인.

- [Kakao MapProjection](https://apis.map.kakao.com/web/documentation/#MapProjection): 컨테이너 픽셀과 좌표 변환.
- [Kakao LatLng.toCoords](https://apis.map.kakao.com/web/documentation/#LatLng_toCoords): 캡처 당시 WCONG 투영 보존.
- [OpenAI 이미지 입력과 한계](https://developers.openai.com/api/docs/guides/images-vision): 이미지 입력과 정밀 공간 추론 한계.
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): Responses API의 JSON 스키마 출력. 스키마 일치가 지도 해석의 정확도를 보장하는 것은 아니다.
